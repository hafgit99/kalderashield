## 6. The NSIS uninstaller

| Field | Value |
| --- | --- |
| Size | 80797 |
| SHA-256 | `55528512acdbdf41d16b3795d140e0b49453eda1ba6c1b7af4d30adcae004a15` |
| Authenticode | NotSigned |
| PE sections | `.text`, `.rdata`, `.data`, `.ndata`, `.rsrc` |
| Embedded `<description>` | Nullsoft Install System v3.11 |

Two facts about this file matter more than its hash.

First, it is generated by Nullsoft Install System and contains no
KalderaShield code. It is not identical to the uninstaller in every other
NSIS installer — an NSIS uninstaller is compiled per project, because the
strings it carries are that project's registry keys, install directory and
file list. What it shares with every other NSIS uninstaller is origin and
shape, not bytes, and that is what the detection is reacting to.

Second, the install directory is a plausible place for malware to write a
persistence executable, and this uninstaller does two things that resemble
that: it is unsigned, and it is the only file in the directory that asks for
elevation. Its embedded manifest requests `requestedExecutionLevel="highestAvailable"`,
which is the default for an NSIS uninstaller that must remove files from a
protected directory. That combination — a newly written unsigned executable
inside a program directory that requests elevation — is a reasonable thing
for a heuristic to score, and it is equally true of the thousands of other
NSIS-based installers on the same hosts.

## 7. Request

1. **Re-evaluate the detection against the hashes in sections 0 and 2.** The file
   accompanying this request is byte-identical to the copy quarantined on
   2026-10-01, and section 4 establishes that it is the same build as the shipped
   portable artifact.

2. **The identifier is a machine-learning class, not a signature.**
   `Troj.Win32.TRX.XXPE50FFF110` belongs to a family Trend Micro also issues against
   unrelated malware, as noted in section 0. A rule in that family can be
   tuned, or given an exclusion for a known-good publisher or build path, in a
   way a signature match cannot. Please confirm whether that is possible for a
   small, publicly auditable project.

3. **Section 5 is the argument for tuning.** The same signature fired on Cargo
   build scripts compiled from unrelated crates and on Nullsoft's own temporary
   uninstaller launcher. If those files are being scored by the same rule, the
   rule is scoring unsigned build output rather than this product, and the
   correct fix is upstream of any single file.

4. **Signing is planned, not refused.** The artifacts here are unsigned because
   the release signing process is not yet in place for this project. With an
   Authenticode signature on the binary, a timestamped and reputable
   reputation build history behind it, and the same source in a public
   repository, this class of heuristic complaint typically disappears. We would
   rather solve it properly than ask for a permanent exception.

5. **If re-classification is not possible**, please advise whether any local
   allow-listing is available to the account, so that development machines
   building from source are not blocked from completing a release.

## 9. Outcome

**The request in section 7 was sent to Trend Micro, and the detections stopped.**

The timeline, as reported by the project maintainer: the request was emailed to
Trend Micro, and within roughly two to three days the product no longer produced
detections on the maintainer's own build machines.

What is deliberately not recorded here: the case reference, the wording of any
reply Trend Micro sent, and the mechanism by which the detections stopped. None of
those were reported back to this document's author, and writing a plausible
version of them would put an unverifiable claim into a report whose entire value
is that every statement in it can be checked. If Trend Micro issued a case number
or confirmed a specific action, that belongs here verbatim with the message it
came from.

Two things about the outcome matter beyond this project:

1. **It was a single vendor.** The detection was Trend Micro's, and the resolution
   is Trend Micro's. Nothing in this report suggests any other vendor was
   contacted or has changed behaviour, and other antivirus products may still
   score these binaries. A user on a different product may still see a warning.
2. **It does not change what the binaries are.** The files are still unsigned.
   Signing remains the general fix rather than a per-vendor exemption, and nothing
   about this resolution should be read as the detection having been a mistake in
   the sense that the files were ever safe to ship unsigned — see section 7.4,
   which argued for signing rather than an exception and was not contradicted.

## 10. Why this is not treated as closing the matter

The resolution removes the blocker on the maintainer's machines. It does not
change the two facts that matter for distribution:

- The Windows artifacts still carry no Authenticode signature, so Windows
  SmartScreen will still warn, and that warning is independent of any antivirus
  vendor's scoring.
- A machine-learning heuristic that fired on unsigned build output can fire again,
  on a different build, or after a vendor's configuration changes. What resolved
  it here was the vendor's action, not a property of the bytes.

Both are stated here rather than left for a reader to infer, because the failure
mode of a resolved false positive is that everyone treats the underlying issue as
closed.
